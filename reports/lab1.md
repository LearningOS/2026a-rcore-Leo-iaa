# 实验一：多道程序与分时多任务

## 实现概述

实现 `sys_trace` 的单字节读、单字节写和系统调用次数查询。每个任务维护独立的调用计数，在统一入口分发前更新，因此当前 trace 调用也计入统计。无效请求返回 -1。计数使用按任务分开的映射，避免在初始化栈上构造大数组。

## 实现说明与验证

调用记录保存在任务管理器中，切换任务不会丢失，也不会读到其他任务的记录。第三章尚未建立用户地址空间，读写按题目定义直接访问地址。使用 `python3 .github/scripts/rcore_grade.py` 调用固定版本官方检查器，运行基础程序、调度和 trace 测试，并检查报告存在性；实际结果保存在 `tmp/rcore-result.json` 和 `tmp/rcore-grade.log`。

本地官方检查结果：7/7，检查器退出码 0，所需报告检查通过。

## 问答

### 1. 用户态执行非法操作

用户程序访问无权限地址会产生访存异常；在 U 态执行 S 态特权指令或访问受限 CSR 会产生非法指令异常。陷入后硬件在 scause 中记录原因，sepc 指向故障指令，stval 按异常类型提供故障地址或辅助信息。内核对应分支打印诊断、终止当前任务并调度下一任务。异常程序的返回路径不会继续执行原本的非法操作。本仓库使用随附的 RustSBI 0.4.1 固件，模拟器为 QEMU 8.2.2。

### 2. `__alltraps` 与 `__restore`

1. 刚进入 `__restore` 时，sp 指向内核栈中保存的 TrapContext。它既用于首次从内核进入用户程序，也用于处理系统调用、中断或异常后恢复用户上下文。
2. `32*8(sp)`、`33*8(sp)` 和 `2*8(sp)` 分别是 sstatus、sepc 和用户态 sp。写回 sstatus 恢复返回时的权限和中断状态；写回 sepc 指定恢复执行的 PC；暂存用户 sp 到 sscratch，为最后交换栈指针做准备。
3. x2 是 sp，恢复它必须留到其他寄存器都加载完成以后，否则无法继续使用当前上下文地址。x4 是 tp，本教学实现不支持用户线程局部存储，保存和恢复时按框架约定跳过它；完整支持 TLS 的系统需要维护该寄存器。
4. 返回前的 `csrrw sp, sscratch, sp` 执行后，sp 为用户栈指针，sscratch 为内核 TrapContext 所在位置，供下次陷入切换使用。
5. 真正返回权限状态的是 `sret`。硬件根据 sstatus.SPP 选择返回的特权级；应用初始上下文将 SPP 设为 User，因而进入 U 态。PC 从 sepc 恢复，中断状态也按架构规定更新。
6. 陷入入口的同名交换指令执行后，sp 指向内核上下文保存区，sscratch 暂存陷入前的用户栈指针，之后把用户 sp 保存到 TrapContext.x[2]。
7. 对系统调用，是 U 态 `ecall` 触发异常后硬件完成到 S 态的切换；对时间中断或访存异常，则由对应事件触发硬件陷入。`__alltraps` 已经运行在 S 态，入口中的交换指令只切换栈，不负责改变特权级。
